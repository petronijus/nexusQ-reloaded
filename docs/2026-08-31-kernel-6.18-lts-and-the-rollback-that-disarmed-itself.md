# 6.18 LTS, three patches that lied about being fine, and a rollback that disarmed itself

2026-08-31. The Q runs **mainline 6.18.48** — 95 stable releases and six minor
versions on from where it sat this morning. The kernel is published, the device
booted it, and the most useful thing found today was not in the kernel at all.

## Why 6.18 and not 7.1

We were on 6.12.12. The 6.12 LTS branch had moved to .107 without us; mainline was
at 7.2.2. `linux-postmarketos-omap` — the same OMAP3/4 family, N900 and Droid 4 —
runs 7.1.5 with only 11 patches, against our 46.

Target chosen: **6.18.48, the newest LTS**. 7.1 would have put us on the same base
as the pmOS omap community, which is worth something, but it is not an LTS and we
maintain this fleet for years. Rebasing 46 patches is not a thing to repeat every
nine weeks.

## The rebase, and why it was cheap

The patch stack was replayed as **git commits**, not edited by hand:
`~/nexusq-build/kstack`, two pristine tarballs committed as independent base
commits. `git rebase --onto` does not need upstream history — it 3-way merges
against the target tree's blobs exactly like `git am -3` — so two 150 MB tarballs
replaced a 5 GB clone of linux.

46 patches in, 44 out, **3 conflicts, all trivial**.

**Two patches were dropped because upstream had independently fixed them**, both
checked by reading the 6.18 source rather than assumed:

- **0004** (twl-core clock cell for TWL6030) — mainline now carries our exact
  `twl_class_is_6030()` condition *plus* a dedicated `twl6030-clk` cell, and
  `clk-twl.c` maps that cell to the same clk32kg + clk32kaudio data. Later
  confirmed on the running device: both clocks are there.
- **0032** (omap-usb-host depopulate on remove) — upstream fixed the same bug in
  the same place, `if (pdev->dev.of_node) of_platform_depopulate()`.

The whole `arch/arm/mach-omap2` block — 12 patches covering VDD_MPU, VC, ABB, OPP,
cpuidle, restart and SMP — had **zero upstream churn** and rebased untouched. The
part everyone expected to hurt did not.

## A clean apply says nothing about compiling

**Three patches applied with zero fuzz and did not build.**

- **0005 / 0029** — upstream constified the sysfs `bin_attribute` API.
- **0007** — upstream migrated clk from `.round_rate` to `.determine_rate(hw, req)`.
  Git's 3-way merge dutifully planted our one-line body into the *new* signature,
  where `rate` and `prate` no longer exist. **The GNU-patch gate cannot see that
  class of hazard**: the hunk applied perfectly, into a function that had changed
  underneath it.

The first two were found one docker build at a time, which is the wrong way: each
round trip costs minutes and holds the shared build volume. The right way, adopted
after the second: **a full kernel build with the local arm-gnu-13.3 cross
toolchain takes 102 s, needs no docker and no volume, and catches all of them in
one pass.** Caveat that belongs next to that recommendation everywhere it appears:
it is gcc 13.3 against glibc headers while the kernel ships built with Alpine
gcc 15.2 for musl, so it is an **API-drift gate, not proof the shipped kernel is
good**.

## Cross-native: 18x, and proven rather than asserted

Every pmbootstrap call in the repo passed `--no-cross`, so every armv7 package was
compiled under qemu — while `pmos/linux-google-steelhead/APKBUILD` had carried
`options="... pmb:cross-native"` all along. The flag was overriding the aport's own
declaration.

    qemu, cold ccache   1983 s
    cross-native         108 s      18.4x

They are **not** bit-identical and cannot be: the compiler driver name is baked
into the image, and `armv7-alpine-linux-musleabihf-gcc …` is 31 bytes longer than
`cc …`, three times over — a 93-byte shift. Equivalence was demonstrated, not
claimed:

1. Strip the 2048-byte Android header, find the LZMA payload (offset 22352),
   decompress both. Both come out at **exactly 19 999 328 bytes**.
2. Of 42 010 differing 4-byte words in the first 12 MB, **99 % carry a small
   constant delta**, dominated by +92. They are ARM `movw` immediates — addresses
   of shifted data, not different code generation.
3. The dense 13-15 MB block is kallsyms, which is address-indexed and so rewrites
   wholesale. That accounts for 2.23M of the 2.34M differing bytes.

The old comments justified `--no-cross` with a `cannot execute cc1: posix_spawn`
toolchain error. That is *also* exactly what a build sees when a concurrent
pmbootstrap zaps its buildroot mid-compile — which happened to this very session.
The original verdict was very likely a misdiagnosis, and the project paid a ~4x
qemu tax on it.

## Results on hardware

Booted in 48 s, health gate auto-promoted it, **dmesg errors: 0**.

| SMP | `nproc: 2` |
| OPP | 350 / 700 / 920 / 1200 MHz, reaches 1200 |
| **VDD_MPU vs OPP** | 350 → 1 025 000 µV, 1200 → 1 380 000 µV, **`vdd_mismatch = 0`** across the series. Stock voltages, exactly. |
| governor | conservative; in a quiet window **78 % at 350 MHz with 417 OPP transitions** — the opposite of the parked-governor signature |
| thermals | quiet-window peak **68.1 °C** vs the 6.12 baseline's 67.5 °C |
| audio | TAS5713, **14 biquad controls**, Speaker + SPDIF cards |
| WiFi / BT / LED / NFC | all up; WiFi MAC from the DTS, BT controller present |

⚠️ Two numbers reported during the session were wrong and are corrected here.
The boot image is **6552 KB, not 5618 KB** — `nq-kernel-ota` carries the boot
slot's 958 080-byte initramfs onto the new kernel, so quote the *staged* size, not
the bare ramdisk-less one; headroom is 104 KB, not 1000. And the thermal "jump to
87.8 °C" compared a loaded window against an idle one; split by reboot it is
82.6 °C (old, under load) against 87.8 °C (new, during boot).

## The find of the day: promote disarmed the rollback

`nq-kernel-ota promote` ends by reconciling the package database with
`apk add --upgrade`. A comment explained that this is safe once the new kernel is
promoted, because "until this point the old package had to stay installed so its
/lib/modules survived a rollback".

**That reasoning is wrong.** `apk` deletes the outgoing package's files, and it
took all **155 modules of 6.12.12-r52** with it — measured, live. But `restore`
exists to put `slot-a-backup.img` — the *old* kernel — back on the boot slot, and
a kernel whose modules have just been deleted comes up with no cfg80211, so no
WiFi, on a box with **no serial console**. The step that tidied up after the
rollback silently disarmed it.

Fixed: the outgoing module tree is stashed across the upgrade and put back,
unowned by apk, for as long as the backup image it belongs to still exists
(`nexusq-kernel-ota` r4, published). The modules were restored on the Prague Q by
hand and verified — both trees present, both with `modules.dep`, cfg80211 there.

**Honest limit: the bug was seen failing; the fix has not been seen working.**
End-to-end proof needs the next kernel OTA cycle.

## Two process findings worth more than the kernel

- **The build volume is single-writer.** `nexusq-workdir` takes one build at a
  time across *all* sessions. pmbootstrap 3.11 announces "Zapping buildroots" on
  every `build`, so whoever starts second deletes the first one's chroots
  mid-compile — and the victim sees a **fake toolchain error**, not a collision.
  `docker ps` before starting anything.
- **`172.16.42.1` is the Lumia now.** The USB-gadget address this repo documents
  as the Q's fallback answers as `nokia-rm875`; the two projects share the gadget
  subnet. `nqctl` in auto mode tries USB *before* WiFi, and it reports the Q as
  unreachable even when it is up, because it resolves the WiFi lease through
  OPNsense — broken since 2026-08-23. Only the `hostname`-first rule caught it.
  The Q currently lives at **192.168.20.246**.

## Still open

- **Ethernet unverified** — no cable attached; patches 0006/0008/0012 only prove
  themselves after a cold power-cycle.
- **HDMI desktop, fastboot-over-ssh (0044), USB-host re-probe, USB Audio latency**
  — not exercised.
- **A 106-package Alpine edge upgrade ran on the device by accident** (an
  `apk upgrade` where `apk add --upgrade nexusq-kernel-ota` was meant). Not
  harmful, but it means the kernel is no longer the only changed variable. If the
  Q misbehaves from here, do not assume 6.18 is the cause.
- Patch **0046** is still worth sending to ASoC: mainline's
  `tas571x_coefficient_info()` still sets `integer.max = 0xffffffff`, which is -1
  in a 32-bit `long`, clamping every biquad write for TAS5717/5719/5733 too.
