# Test plan — kernel 6.12.12 → 6.18.48

A kernel bump is not one change, it is 44. **Every patch in `kernel/patches/` is a
claim about this hardware**, and six minor versions of upstream churn can break any
of them without breaking the build. A boot plus a spot-check proves almost nothing
here, so this file is the checklist, and it is keyed to the patches.

Status legend: ☐ not run · ✅ pass · ❌ fail · ⚠️ degraded

> **Result 2026-08-31: it booted.** Trial-flashed to slot p8 via `nq-kernel-ota
> stage-apk` + `try`, came up in 48 s as `6.18.48-r0`, and the health gate
> auto-promoted it to slot A (md5 `b91d9cab…`). **dmesg errors: 0.** Details per
> item below; two items are still open and one number I first reported was wrong.

## 0. Before anything touches the Q

- ☐ **Is Petr listening right now?** `pactl list short sink-inputs` and a `parec`
  peak *before* mutating any audio path. A quiet gap inside playback is not idle.
  (memory `no-risky-speaker-audio-testing`)
- ☐ Record the current working state so we can prove a regression later: run
  `scripts/diag/nq-collect` on the **running 6.12.12** image and keep the capture.
  Without a before, "it got worse" is an opinion.
- ✅ **Boot image fits — cleared 2026-08-31, but with less room than first claimed.**
  Compare *staged* images, both carrying the same 958 080-byte initramfs:
  6.12 packed 6 506 496 B, 6.18 packs **6 709 248 B** — **~200 KB bigger**, not
  smaller. Still under the ~6656 KB U-Boot caution and far under the 8192 KB
  partition, but headroom dropped from 302 KB to **104 KB**. The earlier
  "736 KB smaller" compared a ramdisk-less image against one with a ramdisk.

## 0b. New this time: the build path itself changed

The kernel is now built **cross-native** (x86_64 chroot, Alpine's armv7 gcc)
instead of under qemu — 108 s instead of 1983 s. Cross-native and qemu kernels
were proven *equivalent* on 2026-08-31 (see memory
`cross-native-kernel-equivalent`: both payloads decompress to exactly
19 999 328 B, and 99 % of the diffs are constant-delta `movw` address shifts from
a 93-byte compiler-name string, plus address-indexed kallsyms).

- ☐ **But no cross-native kernel has ever been booted.** Structural equivalence
  is not a boot. Treat the first one as carrying two new variables — the kernel
  version *and* the build path — and if anything misbehaves, rebuild the same
  tree with `NEXUSQ_KERNEL_NO_CROSS=1` to tell the two apart before debugging
  either. A real source error fails identically on both paths, just 18× slower,
  so that flag is for behaviour differences only, never for a compiler diagnostic.

## 1. Deploy — trial slot only

- ☐ Flash the new kernel to the **trial slot p8 via kernel OTA**, never to the
  production slot. The health gate rolls a bad kernel back with no cable involved.
- ☐ **Prove the rollback works before trusting it.** It has never been exercised
  against a *different kernel version*, and it is the entire safety net for this
  plan. A safety net nobody has seen catch anything is a decoration.
  (memory `test-must-be-seen-failing`, `systemd-oneshot-holds-its-target`)
- ☐ Confirm `/lib/modules/6.18.48-r0/` exists and is populated — with a new
  `pkgver` *and* `pkgrel=0` the module directory name changes, and a rollback that
  cannot find its modules has no cfg80211, so no WiFi, so no way in.

## 2. Boot and the baseline sweep

- ☐ **Full `nexusq-diag` sweep, not a spot check** (memory `run-diag-after-every-boot`).
- ☐ `dmesg` err/warn **empty**. Every boot error on this device is ours
  (memory `all-boot-errors-are-ours`); a new one from 6.18 is a finding, not noise.
- ☐ Both cores up (`nproc` = 2) — patch 0009.

## 3. Per-patch verification

Grouped by what breaks if the patch silently stopped working.

### Power / voltage / OPP — patches 0013-0018, 0023, 0027
The block with **zero upstream churn**, so the expectation is "identical". Any
deviation means the surrounding code moved, not our patch.
- ☐ MPU scales **350 / 700 / 920 / 1200 MHz**; it actually *reaches* 1200.
- ☐ VDD_MPU tracks the OPP (350→1025 mV … 1200→1380 mV), read from the rail, not assumed.
- ☐ ti-abb registers (patch 0018 — the `-ENOTRECOVERABLE` catch-22); FBB at Nitro.
- ☐ Governor is `conservative` with `down_threshold=60` — **and re-check it after
  any governor switch, which resets the tunables** (memory `conservative-down-threshold-retune`,
  `pin-cpu-freq-when-benchmarking`).
- ☐ CPU+power diag is mandatory in every sweep here (memory `always-run-cpu-power-diag`).

### Audio — patches 0001, 0022, 0038, 0041, 0045, 0046
The highest-risk group: `tas571x.c` was the only real rebase conflict, and upstream
added TAS5733 next to our TAS5713 code.
- ☐ TAS5713 probes; playback works through the banana connector.
- ☐ Volume scale is ours, not upstream's (0038) — no software boost.
- ☐ **Biquad EQ writes actually land, verified on the wire, not by read-back**
  (memory `tas5713-biquad-alsa-write-broken`). This is where 0046 lives and where
  upstream's new TAS5733 code shares our fixed `tas571x_coefficient_info()`.
- ☐ McBSP CLKGDV derived from fclk (0022) — sample rate correct, not merely "sound".
- ☐ USB Audio (UAC2 gadget → `alsaloop` → TAS5713) still low-CPU and lip-synced;
  no return of the minutes-long delay (memory `nexusq-usb-audio-latency-finding`).
  Use `PULSE_SERVER=unix:/run/user/10000/pulse/native` — **never `pactl` as root**
  (memory `pactl-as-root-breaks-usb-audio`).
- ☐ Keep volume ≤1-2 %; diagnose from data (dmesg XRUN, `clk_summary`, mixer), not by ear.

### Networking — patches 0006, 0008, 0012, 0021, 0033, 0043
0032 was dropped here; if USB-host re-probe regresses, that drop is the first suspect.
- ☐ **Ethernet after a cold power-cycle** — the historic failure mode, and the one
  0006/0008/0012 exist for. eth0 at 100 Mbit/s full duplex.
- ☐ WiFi associates on 5 GHz; MAC comes from the DTS (0043), not random per boot.
- ☐ brcmfmac loads with no CLM-blob warning (0033) and `mpc=0` is honoured (0021).

### LED ring — patches 0005, 0011, 0029
- ☐ Ring animates. **Wait 300 s before measuring CPU** — a fresh `nexusqd` runs at
  ~1.4 % until the memcmp gate settles it to ~0.07 % (memory `nexusqd-needs-300s-before-measuring`).
- ☐ Ring still alive after a long idle (the AVR-starvation keepalive).

### Bluetooth / NFC — patches 0020, 0036, 0037, 0039, 0040
- ☐ BCM4330 patchram loads (0036), UART at 3M (0040).
- ☐ Pairing works with the permanent NoInputNoOutput agent.
  **Only ever pair against Petr's own phone** (memory `never-touch-devices-we-dont-own`).
- ☐ PN544 probes and activates ISO-DEP targets (0020, 0037).

### Boot / platform — patches 0003, 0009, 0010, 0019, 0024, 0025, 0026, 0028, 0030, 0031, 0034, 0035, 0044
- ☐ `systemctl reboot bootloader` lands in **fastboot** (0044, the SAR scratchpad
  reboot reason). This is what keeps us off the power-cycle, so losing it is expensive.
- ☐ HDMI desktop comes up (0010 pixel-clock cap); LXQt/Wayland on labwc.
- ☐ eMMC/SD settle delay (0028) — no mmc timeouts in dmesg.
- ☐ cpuidle stays **C1-only** (0024). Deeper C-states remain blocked: no serial
  console, so a suspend hang is undebuggable (memory `nexusq-no-serial-access`).

### The two dropped patches — verify the upstream replacements on hardware
Both were verified by reading upstream source. Reading is not running.
- ☐ **0004 → upstream `twl6030-clk`**: confirm `clk32kaudio` actually exists and is
  enabled, since it is the BCM4330 sleep clock. If WiFi/BT misbehave after this
  bump, look here **first**.
- ☐ **0032 → upstream `of_platform_depopulate`**: exercise a USB-host re-probe and
  confirm the EHCI/OHCI children come back.

## 4. Only after all of the above

- ☐ Promote out of the trial slot.
- ☐ Re-run `nq-collect` and **diff against the 6.12.12 capture from step 0**.
- ☐ Send patch 0046 upstream to ASoC — mainline still clamps every biquad
  coefficient write on 32-bit hosts.

## Rule for this whole exercise

If something regressed, **fix the root cause; do not mask it** and do not conclude
the hardware died — it is known-good, so an unresponsive chip is our bring-up bug
(memory `fix-errors-dont-mask`, `never-conclude-dead-hardware`). And the instant a
fix works, bake it into the APKBUILD and rebuild, or a reflash eats it
(memory `bake-successes-into-build`).

  says `linux-google-steelhead-6.12.12-r52`. Cause: `stage-apk` takes a local
  file, but promote's reconcile step resolves against the OTA repo, which has
  never been served 6.18.48. Boot and modules are fine, but `apk fix` would

  all**. Fixing it means publishing the kernel to the OTA repo — a release

- ☐ **Ethernet unverified.** `eth0 down, carrier=0` with no cable attached.

- ☐ **Thermals not yet comparable.** First reported as "67.5 °C → 87.8 °C", which

  numbers are **82.6 °C (old, under load) vs 87.8 °C (new, during boot)**, both
  at 1200 MHz — and the new side is only **36 samples**, nearly all of them boot
  activity. A fair comparison needs a quiet idle window.
- ☐ **Governor behaviour unconfirmed.** Still parked at 1200 MHz at ~300 s uptime,

  quiet window by the OPP *transition rate*, per `conservative-down-threshold-retune`.
- ☐ HDMI desktop, `systemctl reboot bootloader` → fastboot (0044), USB-host

# Idle-power A/B — 2026-08-31 evening

Arm shape `<label>:-:-:-:-:-:-:-` (every governor knob left as shipped), so this
measures the state we ship, not a tuning experiment. Cost is the OPP mix priced by
V²f, normalised to "as if all time at 350 MHz" — CPU time alone says nothing here,
since 1200 MHz costs **6.21×** what 350 MHz does (700 = 2.75×, 920 = 4.34×).

| run | kernel | window | 350 | 700 | 920 | 1200 | trans/min | CPU busy | irq/s | **cost** |
|---|---|---|---|---|---|---|---|---|---|---|
| `k618b` **clean** | 6.18.48 | 2.0 h | 95.3% | 2.5% | 2.0% | 0.2% | 27.1 | 7.79% | 2739 | **1.124×** |
| `k618` *contaminated* | 6.18.48 | 0.8 h | 87.2% | 3.6% | 8.1% | 1.0% | 51.1 | 8.57% | 2789 | 1.387× |
| `allon2` | 6.12.12 | 7.0 h | 86.1% | 11.6% | 1.9% | 0.4% | 84.4 | 9.10% | 2512 | 1.289× |
| `allon3` | 6.12.12 | 8.0 h | 96.6% | 2.8% | 0.2% | 0.4% | 25.9 | 6.21% | 2555 | 1.077× |

**Verdict: no regression.** The clean 6.18 run costs **0.87×** `allon2` and
**1.04×** `allon3` — it lands *inside* the old kernel's own spread, which is
**1.20×** between its two runs. CPU busy is between the two old runs as well.

**The first attempt measured my own collector.** `k618` came out at 1.387× because
the fetch script ssh'd the device once a minute for 50 minutes — 53 logins inside
the measurement window. Same kernel, same config, clean run: 1.124×. **My polling
cost 1.23×**, which is larger than any difference between the kernels, and it
concentrated in the 920 MHz bucket (8.1% → 2.0%). This is exactly what the
`nexusq-idle-attribution-method` note means by *run detached and fetch once*, now
with a number attached.

Caveat, stated rather than hidden: the clean run is not perfectly sterile either —
three ssh connections landed in its final minutes when the collector checked too
early (I computed the end from the study start instead of the arm start). Three
logins in 7200 s against 53 in 3000 s is ~25× lower density, and at the very end
rather than throughout.

One real difference worth watching, not yet explained: the interrupt rate is
**2739/s against ~2530/s on 6.12**, about 8 % higher, consistently across runs.

# Cross-native kernel booted — 2026-08-31 23:14

The last real gap is closed. The **release artifact itself**
(`output/nexusq-boot-v1.15.0.img`, read-back md5 `2970849e…`) was staged to the
trial slot and booted — not a reconstruction of it.

    banner: armv7-alpine-linux-musleabihf-gcc (Alpine 15.2.0) 15.2.0

Up in 46 s, health gate auto-promoted it (slot A md5 `4b1a272a…`), **0 dmesg
errors, 0 failed units**, 63 modules loaded, `nq-collect` verdict **OK**.
`nproc=2`, all four OPPs, `vdd_mpu` 1 380 000 µV at 1200 MHz, `abb_mpu` 1 375 000 µV,
`clk32kaudio` present, TAS5713 with **14 biquad controls**, WiFi on the DTS MAC,
BT controller, NFC, 33 LED devices.

Two things worth keeping from how this went:

- **The two builds ship byte-identical modules.** `cfg80211.ko` is 1 061 336 B and
  `cmp`-identical between the qemu and cross-native apks. The 93-byte
  compiler-name shift lives only in `vmlinux`'s `.rodata`, so there was never a
  MODVERSIONS/ABI risk — the existing `/lib/modules/6.18.48-r0` serves both. This
  is independent evidence for the equivalence argument, found while checking
  whether booting the other build could strand the device.
- **`nq-kernel-ota stage-apk` refuses a same-release apk** ("that apk IS the
  running kernel") because it identifies kernels by release string, and two
  *builds* of `6.18.48-r0` are indistinguishable that way. Use the lower-level
  `nq-kernel-ota stage <boot.img>` for a build-level swap.
- ⚠️ **Do not hard-code ALSA card indices.** The biquad check read card 1 and
  returned 0, which looked like a regression; an HDMI card had appeared at index 1
  and pushed NexusQ-Speaker to card 2, where all 14 controls were present. Same
  mistake was made twice today — find the card by id, not by number.
