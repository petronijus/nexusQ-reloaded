# 2026-11-15 — OTA as a job: an update that cannot be killed, with real progress

On 2026-11-14 the cottage Q took its first update since September (device r117
→ r132, 393 packages). The app reported "apk upgrade did not respond" after a
few minutes, the ring spun for twenty, and a second press finished it. What
happened, and what replaces it.

## What went wrong

- `install_system_update()` ran `apk upgrade --available` inside the bridge
  with `timeout=600`. At 600 s Python SIGKILLed apk at package 260/393. apk 3
  writes its database at the end of a transaction, so the files on disk were
  new and the database said old until the second run reinstalled everything.
- The app waits 60 s for any slow call (`tcp_client.dart`). After that it
  polled `checkSystemUpdate`, which answered `busy` for the whole install,
  gave up after eight tries and said nothing useful.
- Nothing measured progress: the ring spun (`spin`), the app narrated fixed
  sentences, Home Assistant showed a spinner.
- apk ran in the bridge's cgroup, and the bridge restarts itself when its own
  package changes: an update of `nexusq-control` could take apk down with it.

## What apk 3.0.9 offers (checked on the cottage Q and in its source)

- `--cache-dir DIR` on an existing directory makes the package cache active,
  and `--cache-predownload` then splits a transaction in two
  (`src/commit.c`): every package is downloaded into the cache first, **with
  nothing changed on the system**, then installed from the cache.
- `--progress-fd FD` writes `done/total stage` lines (`src/print.c`), the
  stage being `download` then `install`, both weighted as bytes + 64 KiB per
  package (`apk_progress_weight`). Measured with `apk fetch`:
  `131072/505149 fetch` … `505149/505149 fetch`.
- The log lines carry the package counts: `(12/140) Downloading x-1.0-r0`,
  then `(12/393) Upgrading x (1.0-r0 -> 1.1-r0)`.
- `--timeout SECONDS` ends a network connection that makes no progress.

## The design

**A job, outside the bridge.** `installSystemUpdate` and `installNexusUpdate`
start `nexusq-ota@<kind>.service` (`kind` = `system` | `daemons`) and answer
at once with the job. The unit runs `nexusq-control --ota-run <kind>`: the same
file as the bridge (one copy of the apk logic), in its own cgroup, so neither
a bridge restart nor its upgrade can stop it. The bridge only watches.

**Three apk processes.** Whether apk may be stopped is decided by which
process runs, never by reading its output: apk's log and its progress fd are
two pipes, read in whatever order the kernel hands them over, and a late
download line once made an install look like a download (caught by a test).

| Phase | What runs | Interruptible |
|---|---|---|
| `preparing` | `apk update` into the job's cache (`/var/cache/nexusq-ota`), then the plan: `apk upgrade --simulate -vv` (the changes, "Need to download X", "After this operation, Y of additional disk space") | yes |
| `downloading` | `apk fetch` of exactly the plan's packages (`name=version` from its `Installing`/`Upgrading`/… lines) into the cache, under apk's own cache file names (`${name}-${version}.${hash:8}.apk`), so the install finds them cached. Not `apk cache download`: it fetches every package of the solution, changed or not — the whole system for a one-package update (found in review) | yes — nothing is changed, and what was fetched stays for the next try |
| `installing` | `apk upgrade` from the cache, with `--cache-predownload` so a package the download missed is fetched before any file changes | **no** — never signalled; a shutdown waits for it |
| `applying` | `daemon-reexec`/`daemon-reload`, restart the changed daemons, the bridge last (after the job reads `done`) | — |
| `rebooting` | when base libc/init changed (unchanged rule) | — |

The cache is purged (`apk cache purge`) after a successful install. The A/B
slot copy and split (nexusq-rootfs-ab r7) skip and clear it like apk's own.

**Never killed mid-commit.** A download that makes no progress for 5 minutes
is stopped (safe: nothing changed; the cache keeps what came) and the job fails
with that reason. In `installing` a stall only sets `stalled: true`, which the
app and Home Assistant show; apk runs on. The runner never returns while apk
runs: an error reading a line or writing the job file (a full disk at the
switch to the install) is logged and the pipes are drained until apk exits —
the runner leaving early would have systemd SIGKILL apk with it
(`KillMode=mixed`).

**Space.** Before the download: the download (it stays in the cache until the
job is done) plus what apk says the system grows by, plus 192 MiB, must fit in
the free space plus what the cache already holds. A refusal names the Spotify
cache when it is large (librespot keeps 1.5 GiB free and shrinks at its next
start).

**The package lists.** `apk update` exits non-zero when one mirror lags,
and a resumed job starts at boot, often before WiFi. It is tried six times,
30 s apart; after that, a cache that already holds lists goes on with them (a
resumed job needs nothing new), and only an empty one fails the job. Only this
step touches the lists: the plan, the download and the install run with
`--cache-max-age` of a year, because the install (opened for writing) would
otherwise refetch lists older than 4 h and refuse to go on when that fails.
The unit is deliberately not ordered after `network-online.target`: a resumed
start would sit queued behind it.

**Interrupted installs finish themselves** (Petr, 2026-11-14). The job's
durable state is `/var/lib/nexusq/ota/job.json`, written at every phase
change. A bridge that starts and finds a job `running` whose unit is not
active (a power cut, a reboot) starts it again: apk installs what is missing
from the cache and the job applies it. A job interrupted in `rebooting` is
simply done. At most three attempts; then it fails with "interrupted
repeatedly". The watcher reads the unit's cgroup, not `systemctl` (twice a
second for 20 minutes on two cores); without a cgroup it asks systemd, and a
start that is still queued counts as running. A unit whose state cannot be
told is never taken for gone, and a runner started with no `running` record
does nothing, so a late start can never begin an uncounted job. The bridge
does not restart Spotify or AirPlay on a new binary while a job runs. After
apk exits the runner reads its pipes for at most 10 s more (a process a
package script leaves can hold the progress fd open). Live progress goes to `/run/nexusq/ota.json` (tmpfs),
so the eMMC sees a write per phase, not per second.

**Progress, everywhere.**

- Overall `percent`: preparing 0–5, downloading 5–60, installing 60–95,
  applying 95–100 (a phase with nothing to do is skipped). Monotonic.
- `phasePercent`, `packagesDone`/`packagesTotal`, `current` (the package),
  `bytesDone`/`bytesTotal` (download), `etaS`: from the phase's own rate; while
  downloading it adds 1 s per package of the plan for the install (measured
  2026-11-14: 393 packages from the cache in 380 s).
- **The ring** (the runner drives nexusqd itself, the bridge may be
  restarting): the download fills the ring in deep blue (`0 70 160`), the
  install fills it again in bright cyan (`0 200 255`), each 0–100 % of its own
  phase, so the phase is visible from across the room; `preparing` and
  `applying` spin; success is green for 2.5 s; a failure is red for 2.5 s;
  then the theme.
- **The app** gets `updateProgress` events (at most 2 a second, and only when
  something visible changed) and `updateFinished`; `getUpdateJob` returns the
  current or last job, so a reconnect, a reopened app or the Q's reboot shows
  where it stands. Its bar uses the ring's colours for the same phase.
- **Home Assistant**: the update entity carries `in_progress`,
  `update_percentage` and the phase in words, at most every 2 s.
- **Diagnostics**: the snapshot (device r133) has an `UPDATE_JOB` section;
  `nq-health-report` says when a job runs, warns when it is stalled or has
  run for an hour, reports a failed one and packages left in the cache (the
  package lists stay there by design).

**Compatibility.** A client that does not ask for `async` gets the old
blocking answer, now from the job (no 600 s kill). nexusq-mqtt and the app use
`async`. The first update **to** this bridge still runs on the old bridge's
code; every update after it is a job.

## Limits

- Overall percent and ETA are estimates where the phase is unknown in advance
  (install time before the download ends).
- A Q that loses power during `installing` boots with a half-installed system
  and finishes when the bridge starts. Anything that cannot start in that
  state (the bridge itself) is the reflash case it always was.
- A job that resumed lists in `result.changed` only what that attempt
  installed; the reboot before it restarted everything anyway.
- When two repositories carry the same `name-version` as different builds,
  `apk fetch` takes the first, and the solver may want the other: the install's
  `--cache-predownload` then fetches it (before any file changes) without the
  download's stall guard or progress. A wasted download, never a half install;
  our repositories do not overlap like that.
- A trigger that never returns keeps the job, and with it every install and
  check, busy until the Q is rebooted; the diagnostics report it.
- The first device run of this path goes to the Prague Q, with the fault
  injections; the cottage Q takes it only as an ordinary update afterwards.
